# Split fixture and load generators

Run `cargo build --release --locked` in this directory. For an eight-user check across two local generator processes, run `python3 distributed_smoke.py`. The script enrolls ephemeral principals, checks every phase, independently computes the global read, write and delivery counts, and closes all children on timeout. Set `--profile hot` to test skewed membership and writes. The original combined Linux benchmark still accepts its four positional arguments.

## Running across hosts

Use a private authenticated controller channel between each generator and the fixture operator. The runnable smoke controller uses subprocess pipes on one machine. The generator binary can be launched under the same fixed command by a remote controller. Its stdin and stdout carry line-delimited JSON. Distribute only the public enrollment principals. Keep each generator alive through enrollment, load and the final barrier.

1. Launch one `watch-capacity generator FIRST COUNT TOTAL ORGS SECONDS` per shard. Assign contiguous nonoverlapping ranges covering `0..TOTAL` exactly once. At launch the worker writes a `principal` event for each index, followed by `keys_ready`. Private keys stay in that worker's memory.
2. Launch one `watch-capacity serve-external ORGS ROWS BIND_IP SOURCE_IPS`. Supply its stdin with a public principal per line in global index order, then EOF. Set `WATCH_PROFILE=hot` on the fixture for the hot profile; the default is uniform. The fixture returns comma-separated listener URLs and its new public key pin, separated by a space. All listeners share the same process, SQLite store, service and TLS identity. Use the literal interface address reachable by the generators and an explicit comma-separated list of their actual source IPs. Configure peer routing and firewall rules separately. The legacy `serve` command binds only to loopback.
3. At generator launch set `WATCH_GENERATOR_TARGETS` to the fixture's approved literal IP. The default permits only IPv4/IPv6 loopback. Send each generator the same `{"op":"connect","urls":["wss://127.0.0.1:34001/"],"pin":"key:…","profile":"uniform","rate":4,"read_interval_ms":10000}` using the actual fixture announcement. Every assigned destination must pass a pinned, mutual-TLS watch and list call before concurrent enrollment continues. Wait for every `ready` event and verify its session count. The per-port list probes are reported separately from scheduled reads.
4. Send `{"op":"clock"}` several times and record each response's `unix_us` between controller send/receive timestamps. The shortest round trip gives an interval for generator-minus-controller clock offset. Select a common future start far enough ahead to reach all workers, then send each `{"op":"start","unix_us":…}` translated to that generator's wall time. It converts once to monotonic time. Every user's read cadence is staggered by its global index. Only the shard containing an organization's designated writer issues that organization's scheduled writes.
5. Wait for all `result` events before sending any `{"op":"drop"}`. Confirm aggregate runnable sessions, reads, writes and exact watch deliveries. Every worker validates the ordered sequence, organization and 50-row content of every page. Retain sockets through the drop barrier, require `closed` and successful exit from every generator, then terminate the fixture. Treat missing events, malformed messages, a deadline, or any nonzero process exit as a failed run. Apply controller-wide deadlines and reap children on failure.

## Timing and result interpretation

Read and write scheduling latencies use each generator's monotonic clock. For one-way latency each generator obtains five authenticated fixture clock samples before load and five after. For each exchange the fixture timestamp minus generator response/issue time brackets the fixture-minus-generator offset. The shortest sample supplies the reported bounds. A worker timestamps page arrival before validating the page, applies the initial interval's midpoint, and records the estimated time since commit. Negative midpoint estimates within the uncertainty interval round to zero. Inconsistent before/after bounds or a delivery impossibly early at the initial upper bound produce a null `commit_to_receive` histogram. These bounds assume stable clocks between probes. Temporary clock steps during load can escape detection. Report uncertainty with cross-host latency and omit one-way SLO conclusions when it is material.

The `reads`, `writes` and valid `commit_to_receive` results contain HDR `buckets_us` as pairs of bucket upper bound and count. Merge bucket counts across shards before computing percentiles. Add throughput counts across workers. The shard owning user zero alone reports the fixture's counters. That sample is taken after its own result drains. With multiple shards it can precede another shard's last outstanding read. CPU hardware counters and Linux process samples from the combined Linux rung are separate from distributed worker results.
